A fraud monitoring system built on the PaySim dataset and the FinTrace analysis notebook

31 October 2026

FinTrace Fraud Monitor applies the FinTrace notebook's explainable fraud-scoring rules to all 6,362,620 PaySim transactions and presents the results in a seven-page web application. The rules raise 1,154 alerts but catch only 5 of 8,213 labeled frauds at the High threshold. This shows that per-account anomaly rules are better suited to explaining cases than to classifying transactions.

Abstract

Mobile-money fraud is rare, so it is easy to miss in millions of ordinary transactions. This project builds FinTrace Fraud Monitor, a web-based fraud monitoring system over the PaySim dataset of 6,362,620 simulated mobile-money transactions, of which 8,213 (0.129%) are labeled fraud.

The system turns the team's FinTrace analysis notebook into a working application. A build step loads the full dataset into DuckDB and applies the notebook's explainable risk score to all 9,073,900 accounts in about two minutes. A FastAPI backend then serves seven pages: a dashboard, a transaction explorer, a detection engine, risk analysis, fraud analytics, alerts and reports, and model performance.

Evaluated against the dataset's fraud labels, the rule-based score flags 1,138 transactions at the High threshold (score of 50 or more) and catches 5 frauds: precision 0.44% and recall 0.06%. PaySim's own built-in flag is perfectly precise but catches only 16 frauds (recall 0.19%). Exploratory analysis found a much stronger signal that neither detector uses: every TRANSFER or CASH_OUT that moves the sender's entire balance (8,018 of 8,018) is fraud. No machine-learning model was part of the project notebook, so none is reported. The backend includes a slot for one.

1. Introduction

A fraud analyst needs to answer three questions about a suspicious account: who was involved, when its behaviour changed, and why it was flagged. The FinTrace notebook answers these with account-level analysis. It looks at each account's own history, scores how unusual it is, and explains the score in plain language. But a notebook is hard to demonstrate, and it cannot be searched or explored by someone who does not run the code.

Problem statement. Build a fraud monitoring system that runs the project's real scoring logic on the real dataset. It must present the results in a form an analyst can use, and it must not present simulated or invented results as model output.

Objectives

  1. Load and index all 6.36 million PaySim transactions so any transaction or account can be found in under a second.
  2. Apply the notebook's explainable risk score to every account and transaction, and verify it matches the notebook's own code.
  3. Provide seven pages: dashboard, transaction explorer, detection engine, risk analysis, fraud analytics, alerts and reports, and model performance.
  4. Show a 0–100 risk score with Low, Medium and High bands, plus the signals behind each score.
  5. Measure accuracy, precision, recall, F1 and the confusion matrix against the dataset's fraud labels.
  6. Mark every number as dataset fact, rule-based output, or unavailable, and leave a ready API slot for a future machine-learning model.

2. Dataset

The project uses PaySim, a public synthetic dataset that simulates one month of mobile-money transactions (Kaggle). The file PS_20174392719_1491204439457_log.csv is 470 MB and has 6,362,620 rows. Each row is one transaction, and each time step is one simulated hour.

Two properties shape everything that follows. Fraud is extremely rare, so accuracy alone is a misleading measure. And almost every account appears only once, which leaves little history for per-account analysis.

3. System architecture

The heavy computation runs once, offline, so that every page can answer in under half a second.

The build pipeline scores every account in SQL and checks the result against the notebook's Python code. The API then combines fast SQL lookups with the notebook's own functions, run live for whichever account or transaction the user opens.

4. Methodology: the FinTrace risk score

Each account receives a score from 0 to 100. The score is the sum of four signals, each measuring how unusual the account is compared with its own history, and the total is capped at 100. The rules come from section 5 (Explainability) of the FinTrace notebook.

#SignalWhat it measuresWeightMax
1Amount z-scoreShare of the account's transactions more than 2.5 standard deviations from its own meanshare × 10040
2IQR outliersShare of amounts outside Q1 − 1.5·IQR and Q3 + 1.5·IQR (accounts with 4 or more transactions)share × 6025
3Counterparty noveltyShare of the last 5 transactions with a never-seen counterparty, counted only if 40% or moreshare × 3020
4Labeled fraudNumber of the account's transactions already labeled fraudcount × 1535
account score = min(100, wz + wIQR + wnovelty + wlabels)
transaction risk = max(scoresender, scorereceiver)

Avoiding label leakage. Signal 4 reads the fraud labels directly. A detector that uses the labels it is then tested against would look accurate without proving anything. The system therefore keeps two scores:

  • Behavioral score (signals 1–3): used for every verdict, alert, risk band and evaluation metric.
  • Investigative score (signals 1–4): the notebook's default, shown alongside it for case investigation.

Risk bands. Low is below 25, Medium is 25 to 49.9, and High is 50 or above. A High transaction is classified as potentially fraudulent and raises an alert. The notebook's fourth band, Critical (75 or above), is folded into High.

Worked example. Account C760302409 received 9 transactions between steps 18 and 565. Their amounts range from 16,629.95 to 1,767,961.22.

SignalCalculationWeight
Amount z-score1 of 9 amounts (1,767,961.22) is beyond 2.5 standard deviations: 11.1% × 100+11.1
IQR outliers4 of 9 amounts fall outside the fences (Q1 = 171,913, Q3 = 250,572): 44.4% × 60 = 26.7, capped+25.0
Counterparty noveltyAll of the last 5 senders were new: 100% × 30 = 30, capped+20.0
Labeled fraudNone+0
Total56.1 (High)

All 9 of these transactions are labeled legitimate, so the alerts they raise are false positives. In contrast, account C1305486145 sent the fraudulent transaction TXN00000002. It has a single transaction, so only the novelty signal fires and it scores 20.0 (Low). Most PaySim accounts look like this second case: one transaction and a score of exactly 20.

Verification. The scores for all 9.07 million accounts are computed in SQL for speed. The build re-scores 180 random accounts with the notebook's original Python function and compares the two. The result on the full dataset was 0 mismatches.

7. Evaluation

Neither rule-based detector is a usable fraud classifier on PaySim. The FinTrace rules never exceed 0.84% precision, and PaySim's own flag catches only 0.19% of fraud. Both are scored against the isFraud labels on all 6,362,620 transactions; nothing is sampled.

Accuracy is misleading here: the do-nothing baseline scores 99.87%, as high as any detector, because 99.87% of transactions are legitimate. Precision, recall and F1 show the real picture. Recall collapses at threshold 21. That is where transactions whose sender and receiver both score exactly 20, typically accounts with almost no history, stop being flagged; 62.4% of the frauds are of this kind.

8. Discussion and limitations

The FinTrace rules are built to explain unusual accounts to an investigator, and on PaySim they are weak at classifying transactions. The main reason is the data: 94.8% of accounts appear in only one transaction. Such an account has no history to compare against, so the z-score and IQR signals cannot fire, and the novelty signal gives almost every account the same score of 20. The rules work as designed; PaySim gives them little to work with.

The dataset itself carries strong transaction-level signals, such as a sender's whole balance moving out in one TRANSFER or CASH_OUT. A trained classifier would likely learn these. The rules do not use them, because they look at accounts rather than at single transactions.

Limitations

  • Hindsight. As in the notebook, each account is scored on its full 31-day history, so a transaction's risk can reflect later activity. A live system would score only on the past.
  • Synthetic data. PaySim is simulated, and some patterns are artifacts of the simulation. For example, legitimate volume almost stops in the final days while fraud continues. Findings may not carry over to real banking data.
  • In-sample evaluation. The rules have no trained parameters, so testing on the full dataset is fair. However, the "best threshold" figure was chosen on that same data.
  • No community detection at full scale. The notebook's Louvain clustering is not run over all 9 million accounts. The system shows each account's directly connected accounts instead.
  • No machine-learning model. None existed in the project notebook, so no ML results are reported.

9. Conclusion and future work

The project met its objectives. FinTrace Fraud Monitor runs the notebook's own scoring on all 6,362,620 PaySim transactions, matches the notebook on every verified account, and answers any lookup in under half a second. It reports its results honestly: the explainable rules suit case investigation but catch only 0.06% of fraud as a classifier, and the system says so instead of hiding it.

Future work

  1. Train a supervised classifier (for example, gradient boosting) on transaction-level features, evaluate it on a time-based hold-out set, and connect it through the existing model slot.
  2. Add transaction-level rules such as "amount equals the sender's full balance", which the analysis shows is a near-perfect fraud signal on PaySim.
  3. Score accounts using only past activity, so the system could run on a live stream.
  4. Run community detection on the fraud-touching subgraph to surface rings and mule chains.
  5. Validate the approach on a real or less synthetic transaction dataset.
